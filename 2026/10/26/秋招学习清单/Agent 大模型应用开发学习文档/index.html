2. Agent 模式

2.1 ReAct

要点：Reason → Act → Observe 循环。模型先思考需要什么信息，再调用工具，观察结果后继续推理，直到给出答案。

项目对应：云房 Agent 的 Function Calling + 工具结果回填，本质是工具循环；但需要补显式 ReAct 轨迹记录。

面试表达： > 我的 Agent 不是让模型直接回答，而是把业务查询拆成工具调用。模型根据用户问题选择工具，工具返回结构化结果，再把结果送回模型生成分析。为了防止编造，无权限或无数据时返回结构化拒绝载荷。

待补实验：记录一轮 thought/action/observation，对比有无 ReAct 轨迹对工具选择的影响。

2.2 Plan and Execute

要点：先规划步骤，再逐步执行；适合多步任务。与 ReAct 的区别是规划更显式、可审核。

项目对应：云房 Agent 的“市场分析、风险预警、选址参考”天然适合 Plan-Execute。可把一次分析拆成：查指标 → 查预售证 → 算去化 → 生成结论。

待补实验：用 LangGraph 画一个 Planner 节点 + Executor 节点 + Reviewer 节点。

2.3 多 Agent / 工作流

要点：不是所有场景都要多 Agent。单 Agent + 工具 + 状态图通常更稳。多 Agent 适合职责清晰、可并行的子任务。

项目对应：当前单 Agent 足够；短视频项目可拆成“视频理解 Agent”和“商业评估 Agent”两阶段，但工程上仍是流水线。

3. Function Calling 与工具层设计

3.1 工具设计清单

  • 工具名、描述、参数 schema 必须清晰；
  • 参数做类型校验与业务校验；
  • 权限前置：无权限不调用，返回结构化拒绝；
  • 无数据不编造，返回“无数据”载荷；
  • 工具结果要压缩，避免塞爆 Context；
  • 超时、重试、幂等、限流；
  • 记录工具序列，便于评测与排障。

3.2 项目证据

云房 Agent 有 11 个 Function Calling 工具对接真实业务库，包括景气指数、去化预测、预售证检索等；工具层做权限对齐，结构化拒绝载荷 + 防幻觉规则；LLM 不可用时自动降级兜底。

3.3 面试高频问法

Q：工具选择准确率 100% 怎么测？ > 自建 55 条四类评测集，其中工具选择类覆盖应调用、不应调用、无权限、多工具组合等场景；对比期望工具序列与模型实际调用序列。

Q：模型调用错工具怎么办？ > 先做 schema 约束和工具描述优化；再加权限与参数校验；最后用评测集回归。工程上不让模型直接碰数据库，工具层做白名单和拒绝载荷。

4. LangGraph / LangChain / LlamaIndex

4.1 LangGraph

核心：StateGraph、节点、边、条件边、checkpoint、human-in-loop。

项目对应：云房 Agent 用 LangGraph 编排 Qwen2.5-32B，配合 SSE 流式输出和 Redis 多轮会话记忆。

待补： - 给 Agent 加 checkpoint，支持中断恢复； - 加人工审核节点：高风险结论需人工确认； - 对比“纯 Prompt 工具循环”和“状态图编排”的稳定性。

4.2 LlamaIndex

定位：更偏 RAG/QueryEngine/Workflow。需要知道它与 LangChain 的差异：LlamaIndex 对索引、检索、查询管线抽象更重；LangGraph 对状态机编排更重。

待补产出：用 LlamaIndex 复现一个小型 RAG，和云房 RAG 管线做对比。

记忆类型 作用 项目对应

长期记忆 用户偏好、历史结论 待补：用户画像/历史报告摘要

6.2 项目证据

6.3 待补

  • FAISS / Milvus / Chroma 选型对比：数据规模、过滤、持久化、部署成本、生态；
  • 切分策略消融：固定窗口 vs 语义切分 vs 结构化切分；
  • 引用溯源评测：引用是否支持结论；
  • Prompt Injection 防护：检索内容不可信，系统提示词优先级。

7. MCP

7.1 必会概念

  • Host / Client / Server；
  • Tools / Resources / Prompts；
  • 传输：stdio、SSE、HTTP；
  • 安全：工具权限、参数校验、审计日志。

7.2 项目练习

把云房 Agent 的 2~3 个工具封装成 MCP Server：

  1. search_presale_certificate：按社区/时间检索预售证；
  2. get_prosperity_index：查景气指数；
  3. predict_destocking：去化预测。

产出：MCP Server 代码 + 工具 schema + 权限说明 + 调用截图。

面试表达： > 我的项目里工具是业务内嵌的 Function Calling。MCP 的价值是把工具标准化，让不同 Host 复用。我会把无权限、无数据、参数错误都做成结构化返回，并在 Server 侧做白名单和审计。

8. Prompt Engineering 与结构化输出

8.1 要点

  • System Prompt 写角色、边界、拒绝规则；
  • 输出用 JSON Schema / 固定字段；
  • few-shot 给正反例；
  • 解析失败重试 + 降级；
  • 不让模型输出无法验证的结论。

8.2 项目证据

短视频多模态项目：Qwen-VL 视频理解 + MiniMax 商业评估，结构化 Prompt 输出稳定可解析的多维 JSON；FastAPI 异步任务编排、缓存、失败重试、WebSocket 进度推送。

8.3 待补

  • JSON 解析失败重试策略；
  • 结构化输出与 Function Calling 的结合；
  • Prompt 版本管理。

9. 推理部署与性能优化

9.1 指标

  • TTFT：首 Token 延迟；
  • 吞吐：tok/s、req/s；
  • 并发：成功并发数；
  • 成功率；
  • GPU 利用率、显存；
  • 成本：每千 Token / 每请求成本。

9.2 项目证据

  • 云房：Qwen2.5-32B-AWQ 双 4090 TP=2，prefix caching，工具调用解析；并发 8 下吞吐 207 tok/s、TTFT 138ms。
  • TTS：vLLM-Omni 单卡 RTX 4090 部署 Qwen3-TTS-0.6B，并发约 15 → 100，成功率 100%，端到端吞吐约 19 req/s；asyncio 流式并发压测，CosyVoice/Pocket-TTS 横评。

9.3 面试表达

推理优化不是只看吞吐。我会同时看 TTFT、端到端延迟、成功率、显存和成本。TTS 项目里用梯度并发压测和长短文本分组，避免平均值掩盖长尾。

  • 成本统计：输入/输出 Token、模型单价、每请求成本。

11.3 漏洞检测项目的评测补充

独立复现 EMNLP 2025 多阶段漏洞检测方法，补充 Pair-wise Accuracy 与 Token 成本统计。

面试表达： > 评测不只看最终答案。我会拆成工具选择、检索、端到端、权限四层；同时记录 Token 成本和延迟，避免“效果好了但成本不可接受”。

12. 安全与可靠性

  • 权限对齐：无权限不调用工具；
  • 防幻觉：无数据如实告知，拒绝编造；
  • 结构化拒绝载荷；
  • LLM 不可用降级兜底；
  • 工具白名单、参数校验、审计日志；
  • RAG 引用溯源；
  • Prompt Injection：检索内容不可信；
  • 高风险结论人工审核。

13. 面试项目讲述模板

一句话： > 我做过一个房地产智能监测 Agent 平台，用 LangGraph 编排 Qwen2.5-32B，接 11 个 Function Calling 工具，配合 RAG 和 vLLM 自部署，解决了自然语言查询业务库和防幻觉的问题。

STAR： - S：房地产市场数据分散，用户需要自然语言分析； - T：做 Agent 助手，完成市场分析、风险预警、选址参考； - A：LangGraph + Function Calling + Redis 记忆 + RAG 混合检索 + 权限对齐 + vLLM； - R：工具选择 100%、端到端 90%、recall@5 100%、并发 8 吞吐 207 tok/s、TTFT 138ms。

取舍： - 单 Agent 而非多 Agent：稳定、可评测； - 工具层做权限，不让模型直接碰库； - 32B-AWQ 双 4090：成本与效果平衡； - RAG 混合检索 + 重排：提升召回与引用可信度。
